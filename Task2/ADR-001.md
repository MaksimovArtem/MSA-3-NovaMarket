# ADR-001: Агрегирование данных о заказах

 <a name="_hjk0fkfyohdk"></a>**Автор: Максимов Артем**
## 1. Контекст

NovaMarket  - микросервисное приложение, реализующее маркетплейс. Структура описана в Task1/C2.png 
Бизнес хочет реализовать сценарий, в рамках которого у пользователя появится возможность просматривать всю историю своих заказов.
## 2. Требования

Пользователь должен иметь возможность получить информацию об истории своих покупок:
- В списке отображаются все заказы и общая информация
	- Стоимость
	- Дата
	- Способ доставки
- Для каждого заказа доступна подробная информация
	- Список товаров
	- Количество и цена
	- Итоговая сумма
	- Способ доставки
	- Способ оплаты
	- Финальный статус заказа
- Покупатель может скачать чек, оставить отзыв о товаре или заказать его снова.
## 3.  Критерии выбора решения

- Требования к скорости отклика
	Пользователь должен быстро получать ответ 
- Зависимость между сервисами
	Чтение истории не должно затрагивать создание новых заказов
-  Консистентность данных
	Исторические данные должны быть актуальны
- Сложность реализации и поддержки в будущем
- Надежность 
	История должна быть доступна при отказе сервиса создания заказов и наоборот
- Стоимость решения 

## 4.  Решение

### 4.1 Описание

Выбран CQRS с синхронизацией через события. Схема в Task2/C2.png

Команды(запись) реализуются через сервис заказов(Order Service)
Query(чтение) реализуются через новый сервис истории заказов(Order History Service)

Синхронизация идет через события:

- HistoryOrderCreated
	Заказ создан. Отправляется в момент получения сервисом заказов заказа от сервиса корзины(Cart Service). Содержит информацию о товарах, их количестве и стоимости
- HistoryOrderStatusChanged
	Статус заказа изменился. Отправляется каждый раз, когда сервис заказов узнает об изменении статуса заказа
	Возможные статусы:
		- Заказ подтвержден
		- Заказ оплачен
		- Заказ передан в доставку
		- Заказ завершен
		- Заказ отменен
	Кроме статуса содержит метаинформацию, связанную с перечисленными статусами. Например, id транзакции оплаты, время изменения статуса и тд
- HistoryDeliveryCreated
	Доставка создана. Отправляется в момент получения сервисом заказов события DeliveryCreated. Содержит информацию о доставке: компания, трекинг-идентификатор и тд
- HistoryDeliveryStatusChanged
	Статус доставки изменился Отправляется каждый раз, когда сервис заказов узнает об изменении статуса доставки

События сознательно дублируют уже имеющиеся события в системе. Необходимо для того, чтобы источником правды для сервиса истории заказов был сервис заказов и не случилось ситуации, когда, например, изменение статуса доставки попало в сервис истории заказов, но не попало в сервис заказов

### 4.2 Соответствие критериям

- Все данные хранятся локально в сервисе, поэтому
	- Пользователь будет быстро получать ответ
	- Пользователь сможет получить ответ даже если сервис заказов временно недоступен
- Консистентность данных обеспечивается тем, что источником событий является сервис заказов. Однако из-за событийной модели что-то в теории может быть утеряно
- Выбранный метод не является самым дешевым с точки зрения начальной реализации, но зато он относительно легко расширяем добавлением новых событий 
- Метод не является самым дешевым, тк требует развертывания Kafka для работы с событиями и реализации всех описанных событий

## 5. Альтернативы

### 5.1 **API Composition**  

Запрос к сервисам заказов, доставки и оплаты для получения текущего состояния

- Скорость отклика ниже, чем в выбранном сценарии из-за необходимости опрашивать другие сервисы
- Зависимость от работы других сервисов и влияние на скорость их работы "лишними" запросами
- Данные консистентны, тк напрямую запрашиваются актуальные в моменте
- Начальная реализация является самой простой из всех альтернатив, но расширение будет дороже, тк по сути каждое расширение это новая обработка новых запросов к сервисам 
- Вариант является самим дешевым в плане реализации

### 5.2 Event Sourcing

Хранение цепочки событий в сервисе заказов
- Все данные хранятся локально в сервисе, поэтому пользователь будет быстро получать ответ
- Невозможно посмотреть историю при отключении сервиса заказов
- Консистентность данных обеспечивается тем, что работа идет в "мозге" всей системы - сервисе заказов
- Самый сложный способ из альтернатив в плане реализации
- Дорогой в разработке из-за своей сложности
## 6. Последствия  

- Появление нового сервиса со своей базой 
- Дублирование части уже имеющихся событий
	- Необходимость поддерживать события актуальными 
- Фронтенд получает быстрый отклик без запросов к другим сервисам
